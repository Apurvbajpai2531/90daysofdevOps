# Day 52 – Kubernetes Namespaces and Deployments

## 🎯 Objective

The goal of Day 52 was to understand how Kubernetes organizes resources using **Namespaces** and manages applications using **Deployments**. Unlike standalone Pods, Deployments provide self-healing, scaling, and rolling update capabilities, making them the preferred way to run applications in production.

---

# What are Namespaces?

Namespaces are logical partitions within a Kubernetes cluster that help organize and isolate resources.

They are commonly used to separate different environments such as:

* Development
* Testing
* Staging
* Production

Built-in namespaces include:

* **default** – Default namespace for resources.
* **kube-system** – Kubernetes control plane components.
* **kube-public** – Publicly readable resources.
* **kube-node-lease** – Stores node heartbeat information.

# Deployment Manifest

Example Deployment:

```yaml id="1q6xui"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  namespace: dev
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80
```

---

# Deployment Components

### apiVersion

Defines the Kubernetes API version.

### kind

Specifies the resource type.

### metadata

Contains resource identity such as:

* Name
* Namespace
* Labels

### spec

Defines the desired state.

Includes:

* Replica count
* Pod selector
* Pod template
* Container image
* Ports

# Self-Healing

One Pod managed by the Deployment was deleted manually.

```bash id="rlsl6l"
kubectl delete pod <pod-name> -n dev
```

Kubernetes automatically detected the missing Pod and created a replacement.

This demonstrates the self-healing capability of Deployments.

---

# Scaling

Scaled the Deployment using:

```bash id="dqjlwm"
kubectl scale deployment nginx-deployment --replicas=5 -n dev
```

Later reduced replicas:

```bash id="g1ptdb"
kubectl scale deployment nginx-deployment --replicas=2 -n dev
```

Scaling can also be performed declaratively by modifying the YAML manifest and reapplying it.

---

# Rolling Update

Updated the container image:

```bash id="6vrc7k"
kubectl set image deployment/nginx-deployment nginx=nginx:1.25 -n dev
```

Verified rollout:

```bash id="rg7q9i"
kubectl rollout status deployment/nginx-deployment -n dev
```

Viewed rollout history:

```bash id="lwk0ku"
kubectl rollout history deployment/nginx-deployment -n dev
```

Performed rollback:

```bash id="mxiv2j"
kubectl rollout undo deployment/nginx-deployment -n dev
```

The Deployment safely returned to the previous image version without downtime.

---

# Standalone Pod vs Deployment

| Standalone Pod                 | Deployment                          |
| ------------------------------ | ----------------------------------- |
| Single Pod                     | Manages multiple Pods               |
| No self-healing                | Automatically recreates failed Pods |
| Manual scaling                 | Automatic scaling support           |
| No rolling updates             | Supports rolling updates            |
| No rollback                    | Supports rollback                   |
| Not recommended for production | Production-ready                    |
